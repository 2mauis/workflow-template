# Workflow v2.2 评审报告

语言：**简体中文** · [English](v2.2-review.en.md)

日期：2026-11-15。对象：本模板仓库的全部文件，即规则正文 `template/docs/workflow-v2.md`、`template/AGENTS.md.template`、PR/验收/交接/spec 模板、Cookbook、采用指南、README 和 CHANGELOG（中英文）。

本报告回答三个问题：v2.2 的规则各自出自哪里；公开资料里的做法与本模板有哪些相同和不同；全仓评审发现了什么、怎么处理的。本报告取代此前合入的同名文件，旧版中与公开原文对不上的说法已改正（见 S2-8）。

## 1. 方法

- **来源核对**：下文每个链接都在 2026-11-15 打开原文核对过。引号内是原文摘录（英文），引号外是本报告的转述。
- **演讲的核对依据**：poteto 的演讲按该公开帖所附视频的自动生成英文字幕核对。机器字幕可能有错字，引用演讲处都以字幕为准。
- **观察与推断分开**：原文里有对应句子的写作「观察」；本报告由原文引申出的结论标「推断」。
- **没有公开出处的规则**：写「来源为内部笔记」，不把内部材料列为参考文献。公开资料在这些条目上只作旁证。
- **分级**：S1 和挡合并或主流程的 S2 在本轮直接改文件；其余 S2 和 S3 只登记。例外是 S2-10：它不挡合并，但属于收紧，经负责人决定在本轮写入规则正文。会放宽审批红线的做法只登记、不采纳。
- **不写的内容**：除下文 2.2 节对 poteto 的既有写法外，本报告不写个人姓名，不写花费或用量，不写地址或城市。机构发布的文章按机构署名引用。

对这组资料的三点观察：

1. **人的批准不能由机器代替，这一点各篇一致。** A1 写明 agent 的批准不算人的批准；A8 写明自动评审不批准也不阻止 PR，合并的决定留在团队手里；A10 写明使用者对批准的内容负责。
2. **A1 同时描述了一种比本模板更宽的做法。** 低风险改动在自动评审和安全检查通过后可以没有人工批准。原文给这条加了前提："Only trusted authors get the lighter paths."，并建议 "start strict and loosen with evidence"；原文也承认 "We don't yet have circuit breakers that tighten approval when those numbers move"。本模板不采纳，见 N1。
3. **云端会话能推到哪些分支，两处公开说法不完全一样。** A6 写会话凭据只能推到自己的工作分支；A10 写由托管平台按仓库的分支保护规则决定，并提醒 "A rule that access can bypass doesn't block a session's push"。**推断**：不能假定平台一定拦得住对 main 的推送，停止点必须写在规则里并由人执行，不能寄托在某个工具的默认限制上。

### 2.2 poteto 的开发流程

「poteto」指的是公开身份为 lauren（X 帐号 [@poteto](https://x.com/poteto)）的一篇 38 分钟演讲，以及同名原帖。原帖：https://x.com/poteto/status/2102050467505430555 （2026-09-21）。标题为 “here's how i shipped 2,500 PRs last month to production”。演讲原为一次公开活动准备，后把视频放到该帖。作者在公开简介和演讲开场中称自己在做 Grok Bot。

口头数量与标题不一致：标题写 2,500；开场口头说 "shipped 2,000 pull requests"，后面又说了一次 2,000。本报告并列记录，不裁决哪个数字为准。

名称上的差别：任务里把这个来源叫作「xAI poteto」。原帖正文和字幕里没有出现 “xAI”；公开简介和演讲开场（按字幕）写的机构名是 SpaceX AI。本报告按公开原文记录，不对机构名称下结论。

演讲中与本 workflow 相关的内容（观察，按字幕）：

- **瓶颈是信任。** 无法把并行的 agent 从几个扩到上百个，是因为 "you don't have trust in your agent's work yet"；作者说 "I am the bottleneck"。
- **人仍对结果负责。** "we're still responsible for the final outcome"。
- **用可检查的证据建立信任。** 让 agent 自己把应用跑起来，采集 trace 和堆快照，拿出 "empirical evidence" 证明代码有效、性能达标；形式化方法是其中最难、尚未解决的一端。
- **代码库是 agent 的记忆。** agent 喜欢沿用已有写法，所以坏写法会 "spread kind of like a virus"。
- **纠错有先后顺序。** 发现 agent 反复犯同一类错时，按强到弱依次考虑：通过代码库、架构和数据结构让这种写法 "categorically impossible"；静态分析（lint、编译器诊断、CI）；规则、自动评审机器人和技能（只是引导，不能强制）；风格指南（"really only enforceable by humans in a code review"）。看到坏写法时先 "write a lint rule"，不必马上清理存量，至少 "stop the bleeding"。
- **外层自动化。** 用连接器和定时任务启动云端 agent，自动复现缺陷报告并自动开 PR。

演讲没有讲的内容（观察）：审批门禁、合并由谁批准、先写规格。所以演讲里没有任何内容可以用来放宽本模板的审批红线，也没有内容直接支持本模板的停止点清单。

同一作者公开的技能集 [pstack](https://github.com/cursor/plugins/tree/main/pstack) 的说明文档可以补充几点（观察）：

- `/tdd` 先写失败的测试再修复，与本模板的红绿顺序一致。
- `/correct` 把反复出现的一类错误修在 "the highest level that works"，文档放在最后，与演讲里的纠错顺序一致。
- 原则 `prove-it-works` 要求对照真实产物验证；`encode-lessons-in-structure` 要求把教训写进结构而不是只写进说明。
- 与本模板不同的地方：说明里写 "i don't believe in planning." 和 "the best spec is code."；原则 `never-block-on-the-human` 只在不可逆动作上保留确认；`autopilot-full` 让 agent 把各自的 PR 一路推进到合并，另有一个不含合并的 `autopilot-stack`。本模板不采纳这几条，见 N3、N4。

## 5. 分级约定

- **S1**：会破坏审批、安全、隐私或署名真实性，或导致错误合入或部署。

## 8. S3（只登记）

1. **独立评审的收敛规则。** 轮次上限、后几轮只审新 diff、不重复已提过的发现。依据：A1 "A round cap. After three rounds, the reviewer asks the author to step back and reconsider the approach."。
2. **给评审发现加“既有问题”标记。** 不是本次改动引入的问题单独标出，登记而不算在本轮头上。依据：A1 的标签 "Important, Nit, or Pre-existing"。
3. **把纠错顺序写成复盘的可选做法。** 复盘时先问能否让这类错误写不出来，其次加静态检查，再次才是规则、技能和说明文字。依据：[poteto 演讲](https://x.com/poteto/status/2102050467505430555)、pstack 的 `/correct`。
4. **「Spec 和证据」补充非测试类证据的例子。** 实际运行输出、trace、截图，与测试并列，不代替测试。依据：A1 第一层检查 "ask it to show the output instead of saying it's done"；poteto 演讲。
5. **写明“谁合入谁负责”。** 合并后的责任归属，不是额外的批准人。依据：A1 "Owning the outcome. A person is accountable for every change that ships, whoever typed it."。
6. **长任务的进度文件和检查点与交接记录互相引用。** 依据：A5、A11。
7. **任务书和评审提示写明本轮不看的类别。** 例如纯风格问题，以减少评审噪声。依据：A3（见 2.1 的摘录）；A1 "Noise costs more when the author is an agent."。
8. **把云端环境的网络访问范围列为适配表的一项。** 依据：A9 的主机白名单；A10 "Network access is limited by default and can be configured to be disabled or allow only specific domains"。
9. **提供独立的任务书模板。** README 已注明尚无独立模板，目前内联在规则正文和 Cookbook 里。依据：A11 对任务描述的要求。
10. **默认分工点名了具体产品和模型。** 可在适配表覆盖，但名称会随时间过期；可考虑正文只写角色，默认值只放在适配表。依据：本仓库“角色按职责划分，不按产品或厂商”的原则。
11. **工具自带的 trailer 怎么处理。** A6 写云端会话的提交带有指回会话记录的 trailer。本模板只规定了 `Code-Tool` 和 `Host-Id`，没有说工具自动加的 trailer 是否保留，也没有说公开历史里出现会话链接是否可以接受。需要负责人决定。
12. **Cookbook 的两处表述。** 标题和开头用了一个代称来指执行者，是否保留由负责人决定；加强测试以竞态检测、连跑和开关极性为例，可以写明它们是示例（正文已有“适用时”）。

## 9. 只登记、不采纳

以下做法出自公开来源，但会放宽本模板的审批红线或与既定规则相反，本轮不采纳。要采纳其中任何一条，都属于改门禁，须由用户另行批准。

- **N1 低风险改动免人工批准合并。** A1：低风险一档在自动评审和安全检查通过后不需要人工批准；文末还提到其内部仓库允许负责人决定哪些低风险改动只凭自动检查合并。本模板要求每次合并由用户本人批准，维持不变。原文自己给出的前提（只对受信任的作者、从严开始并凭证据放宽、尚无自动收紧的熔断机制）本模板都不具备。
- **N2 作者写明理由后自行关闭误报。** A1："You either fix it or close the thread with a short reason, which is how you clear a false positive."。本模板对隐私与凭据扫描更严：任何命中先停下上报，不得自行加入白名单。维持不变。
- **N3 不做计划、以代码为规格。** pstack 说明："i don't believe in planning."、"the best spec is code."。本模板保留规格和设计评审在先。
- **N4 agent 自行推进到合并，只在不可逆动作上等人。** pstack 的 `autopilot-full` 和 `never-block-on-the-human`；A6 也提到定时任务在没有批准提示的情况下运行并推送到带前缀的分支。本模板的停止点清单不变；云端环境只能向约定分支推送和开 Draft PR。
