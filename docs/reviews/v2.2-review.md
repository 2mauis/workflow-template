### poteto 的开发流程

「poteto」指的是公开身份为 lauren（X 帐号 [@poteto](https://x.com/poteto)）的一篇 38 分钟演讲，以及同名原帖。原帖：https://x.com/poteto/status/2102050467505430555 （2026-09-21）。标题为 “here's how i shipped 2,500 PRs last month to production”。演讲原为一次公开活动准备，后把视频放到该帖。作者在公开简介和演讲开场中称自己在做 Grok Bot。

口头数量与标题不一致：标题写 2,500；开场口头说 shipped 2,000 pull requests to production。本报告并列记录，不以二手摘要裁决哪个数字为准。核对依据是该公开帖所附视频的自动字幕，不是内部转写。

演讲中可公开引用、且与本 workflow 相关的要点：

- 扩展 agent 的瓶颈是信任，不是把更多会话同时拉起。
- 代码库就是 agent 的记忆；错误写法会像惯例一样被复制。
- 纠错优先级从强到弱：让错误在代码库/架构里写不出来；静态检查（lint、编译、CI）；规则或自动审查机器人；技能（skills）；风格指南最弱。
- 要让 agent 用可检查的证据（运行应用、trace、截图）证明改动生效，而不是只靠说明。
- 目标是把人从重复瓶颈里拿开，但人对最终结果仍负责。

## S2

1. **正文引用了尚未存在的评审文件（已在本轮补上）。** `template/docs/workflow-v2.md` 的 v2.2 变更记录指向 `docs/reviews/v2.2-review.md` 与 `docs/reviews/v2.2-review.en.md`。文件缺失会使「来源与评审依据」无法核验。本轮已写入这两份报告。依据：模板自身的可追溯要求，以及 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 对可检查输出的强调。
2. **配套文档与规则正文不同步（已在本轮对齐）。** 规则文件与 AGENTS 模板先完成了更精确的表述（S2 须标明是否阻挡、登记不等于豁免、扫描不得自行加白名单、Host-Id 只用约定 id、下一轮登记位置等），README、Cookbook、采用指南和仓库 CHANGELOG 仍停留在更早草稿。不一致会让执行者按不同文本操作。本轮已中英同步。
3. **「放宽测试或门禁保证」曾从规则清单中消失（已恢复）。** 这不是 v2.1 原清单里的条目，而是 v2.2 拟新增的收紧项：任何放宽测试或门禁保证的改动必须停下等用户批准。若只写在 Cookbook / CHANGELOG、不写进规则正文，执行者会漏掉。恢复该项是收紧，不是放宽原红线。
4. **「每次部署单独批准」写得不够明确（已补句）。** 「部署」本身已是停止点，但未写明不能沿用前一次部署批准。这与「每次外部动作单独授权」的既有精神一致，本轮在清单里写清。
5. **Anthropic 博客中的风险分级审批与本模板红线不同（只登记，不改正文）。** [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) 按改动风险决定要几位人工批准，低风险项可以没有人工批准。本模板要求合并和部署必须由用户本人批准。若按原文改模板，就会放宽现有审批红线，故只写在报告里，不改正文。

## S3（本轮不改模板，留到下一轮）

1. 把 poteto 的纠错优先级写成可选实践：优先改代码库与静态检查，再靠规则、技能和风格指南。依据：[原帖及演讲](https://x.com/poteto/status/2102050467505430555)。
2. 在「Spec 和证据」中补充非测试类自证例子（截图、运行 trace），与先红测试并列，但不替代测试。依据：[code review 文中的开 PR 前自证](https://claude.dev/blog/solving-code-review-at-anthropic/)、[poteto 演讲中的可验证证据](https://x.com/poteto/status/2102050467505430555)。
3. 为独立评审增加收敛规则：轮次上限、后续只审新 diff、不重复已关闭的发现。依据：[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)。
4. 把「谁合并，谁负责」写成合并后的责任归属，而不是额外的批准人。依据：同上。
5. 在采用指南中注明 Claude Code 最佳实践的现行地址是文档站，旧工程博客地址会重定向。依据：https://code.claude.com/docs/en/best-practices
6. Cookbook 里加强测试仍以竞态、连跑和开关极性为例，可以再写明这是示例而不是每个语言的强制项（正文已有「适用时」）。依据：保持模板通用，避免绑定单一工具链。
7. 长时任务的检查点与可恢复环境，可与「任务书 / 交接」互参。依据：[Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。
