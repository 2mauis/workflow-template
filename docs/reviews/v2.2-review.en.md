# Workflow v2.2 review

Date: 2026-11-15. Scope: the workflow rules and companion documents in this template repository (`template/docs/workflow-v2.md`, `template/AGENTS.md.template`, the Cookbook, the adoption guide, and the README, in Chinese and English). Method: check the public primary sources first, then compare v2.1 and the constraints proposed for v2.2, and grade findings as S1, S2, or S3. Each finding includes a source link. This round follows MVP iteration: only S1 issues and S2 issues that block the main flow are written into the templates; S3 issues are logged.

This report cites public sources only. Claims that have no checked public original are marked "source: internal notes" and the internal notes themselves are not listed as references.

### poteto's development process

"poteto" refers to a 38-minute talk by lauren (the X account [@poteto](https://x.com/poteto)) and the post that hosts it: https://x.com/poteto/status/2102050467505430555 (21 Sep 2026). The title is "here's how i shipped 2,500 PRs last month to production". The talk was prepared for a public event and later posted on X. In the public profile and at the start of the talk, the author says they work on Grok Bot.

The title and the spoken figure differ. The title says 2,500; the opening of the talk says "shipped 2,000 pull requests to production". This report records both and does not decide between them from a secondary summary. The check used the auto-generated captions on the public video attached to that post.

Points from the talk that are relevant to this workflow:

- Trust, not the number of sessions started at once, is the limit on scaling agents.
- The codebase is memory for agents; a bad pattern will be copied as if it were convention.
- Correction, from strongest to weakest: make the mistake unrepresentable in the codebase or architecture; static checks (lint, the compiler, CI); rules or an automated review bot; skills; style guides last.
- Agents should prove a change with inspectable evidence (running the app, traces, screenshots), not only with a description.
- The aim is to take the person out of the repetitive bottleneck; the person still owns the final outcome.

## Severity

- S1: would break approval, safety, or truthful attribution, or would let a change merge or deploy incorrectly.
- S2: would block the main flow or a merge, or would make the rules disagree with each other.
- S3: improvements to practice, wording, or maintainability; logged only in this round.

## S1

No S1 issue was found that should block publishing this version. The v2.1 approval red lines (merging to main, deployment, rewriting pushed history, credentials, policy files, and new dependencies) are not loosened in v2.2.

[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) also states that a bot approval cannot replace a person and that an approval is tied to a specific commit. This template keeps "an approval from another agent or bot is not user approval," which agrees with that source and is not treated as a defect.

## S2

1. **The rules cited review files that did not yet exist (fixed in this round).** The v2.2 change log in `template/docs/workflow-v2.md` points to `docs/reviews/v2.2-review.md` and `docs/reviews/v2.2-review.en.md`. Missing files would make the stated review basis unverifiable. Both reports are added in this round. Basis: the template's own traceability rules, and the emphasis on inspectable output in [Building effective agents](https://www.anthropic.com/research/building-effective-agents).
2. **Companion documents were out of sync with the rules (aligned in this round).** The rules file and the AGENTS template already used more precise wording (mark whether an S2 issue blocks, logging does not waive an item, scan hits may not be allowlisted by the agent, Host-Id is only the agreed id, a configurable next-round log location). The README, Cookbook, adoption guide, and repository CHANGELOG still matched an earlier draft. That split would let an implementer follow two different texts. Chinese and English companion docs are synced in this round.
3. **"Relaxing a test or gate guarantee" had dropped out of the rules list (restored).** This item was not in the v2.1 list; it is a v2.2 tightening: any relaxation of a test or gate guarantee must stop and wait for user approval. If it lived only in the Cookbook or CHANGELOG, implementers would miss it. Restoring it tightens the list; it does not loosen the previous red lines.
4. **"Each deployment needs its own approval" was not explicit (clarified).** Deployment was already a stop point, but the text did not say a previous deployment approval cannot be reused. That matches the existing rule that each external action is authorized separately. This round states it in the list.
5. **The risk-tiered approval in the Anthropic blog is not adopted (logged only; the rules are not changed).** [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) lets the risk of the change decide how many human approvals are required, including none for low-risk changes. This template requires the user in person to approve merges and deployments. Changing the template to match that article would loosen the current approval red lines, so the idea stays in this report and is not applied to the rules.

## S3 (logged only; not written into the templates in this round)

1. Optionally record poteto's correction order: change the codebase and static checks first, then rules, skills, and style guides. Source: [the post and talk](https://x.com/poteto/status/2102050467505430555).
2. In "Specs and evidence," add non-test examples of self-proof (screenshots, runtime traces) alongside failing tests first, without replacing tests. Sources: [self-proof before a PR](https://claude.dev/blog/solving-code-review-at-anthropic/) and [inspectable evidence in the talk](https://x.com/poteto/status/2102050467505430555).
3. Add convergence rules for independent review: a cap on rounds, later rounds review only the new diff, and do not repeat findings that were already closed. Source: [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/).
4. Record "you land it, you own it" as post-merge ownership, not as an extra approver. Source: the same article.
5. Note in the adoption guide that the current Claude Code best-practices URL is the documentation site, and that the old engineering-blog URL redirects. Source: https://code.claude.com/docs/en/best-practices
6. The Cookbook still uses race detection, repeated runs, and switch polarity as examples of strengthened tests; it can say more clearly that these are examples, not mandates for every language (the rules already say "where applicable"). Basis: keep the template generic and avoid tying it to one toolchain.
7. Checkpoints and a recoverable environment for long-running work can cross-reference the task brief and handoff sections. Source: [Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents).

## Adopted in this round

Written into the v2.2 rules (Chinese and English kept in sync):

- MVP iteration; each S2 issue must be marked as blocking or not; logging does not waive an item.
- Strengthened tests and independent review form one handoff; stop-point items and scan hits are still reported immediately.
- The cloud coding environment is a full working environment, without changing the stop points; confirm authorization before submitting; state the base branch when there is no branch picker; retry and verify authorization or branch failures.
- An approval from another agent or bot is not user approval; each deployment needs its own approval; "relaxing a test or gate guarantee" is added.
- Host-Id carries only the agreed id; scan hits may not be added to an allowlist by the agent; branches are not deleted without an instruction; the next-round log location is configurable.
- The "Terms, plans, and communication" section.

Not adopted (it would change an approval red line): skipping human approval for low-risk merges, as described in S2-5.
