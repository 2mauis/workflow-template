# Workflow v2.2 review

Language: **English** · [简体中文](v2.2-review.md)

Date: 2026-11-15. Scope: every file in this template repository, that is, the rules in `template/docs/workflow-v2.md`, `template/AGENTS.md.template`, the PR, acceptance, handoff, and spec templates, the Cookbook, the adoption guide, the README, and the CHANGELOG (Chinese and English).

This report answers three questions: where each v2.2 rule comes from; how the practices in public sources agree with or differ from this template; and what the full review found and how each finding was handled. It replaces the earlier file of the same name; statements in that version that did not match the public originals are corrected (see S2-8).

## 1. Method

- **Checking sources**: every link below was opened and checked against the original on 2026-11-15. Text in quotation marks is taken from the original; text outside them is this report's paraphrase.
- **Basis for the talk**: poteto's talk was checked against the auto-generated English captions on the public video attached to the post. Machine captions can contain errors, and every reference to the talk follows the captions.
- **Observations and inferences are separate**: a statement with a matching sentence in the original is an observation; a conclusion this report draws from the original is marked **Inference**.
- **Rules with no public source**: these are marked "source: internal notes," and internal material is not listed as a reference. Public sources serve only as supporting evidence for those rules.
- **Grading**: S1 issues and S2 issues that block a merge or the main flow are fixed in the files in this round; other S2 issues and S3 issues are logged. The exception is S2-10: it does not block a merge, but it is a tightening, and by the owner's decision it is written into the rules in this round. A practice that would loosen an approval red line is logged and not adopted.
- **What is left out**: apart from the existing wording about poteto in section 2.2, this report gives no personal names, no cost or usage figures, and no addresses or cities. Articles published by an organization are cited under the organization.

Three observations about these sources:

1. **They agree that a machine cannot stand in for a person's approval.** A1 says an agent's approval does not count as a person's; A8 says automated review neither approves nor blocks a PR and the merge decision stays with the team; A10 says the person approving is responsible for what they approve.
2. **A1 also describes a practice looser than this template.** A low-risk change may need no human approval once automated review and security checks pass. The original attaches conditions: "Only trusted authors get the lighter paths.", and it recommends to "start strict and loosen with evidence"; it also acknowledges "We don't yet have circuit breakers that tighten approval when those numbers move". This template does not adopt it; see N1.
3. **Two public statements about which branches a cloud session can push to are not identical.** A6 says the session credential can push only to its own working branch; A10 says the hosting platform decides by applying the repository's branch protection rules, and warns that "A rule that access can bypass doesn't block a session's push". **Inference**: a project cannot assume the platform will always stop a push to main, so stop points have to be written in the rules and carried out by people, not left to a tool's default limits.

### 2.2 poteto's development process

"poteto" refers to a 38-minute talk by lauren (the X account [@poteto](https://x.com/poteto)) and the post that hosts it: https://x.com/poteto/status/2102050467505430555 (21 Sep 2026). The title is "here's how i shipped 2,500 PRs last month to production". The talk was prepared for a public event and later posted on X. In the public profile and at the start of the talk, the author says they work on Grok Bot.

The title and the spoken figure differ. The title says 2,500; the opening of the talk says "shipped 2,000 pull requests", and 2,000 is repeated later. This report records both and does not decide between them.

A difference in naming: the task called this source "xAI poteto." The text of the post and the captions do not contain "xAI"; the public profile and the opening of the talk (per the captions) name the organization as SpaceX AI. This report records what the public originals say and draws no conclusion about the organization's name.

What the talk says that bears on this workflow (observations, per the captions):

- **Trust is the bottleneck.** A team cannot go from a few parallel agents to a hundred because "you don't have trust in your agent's work yet"; the author says "I am the bottleneck".
- **People still own the result.** "we're still responsible for the final outcome".
- **Trust is built from inspectable evidence.** The agent runs the application itself, collects traces and heap snapshots, and produces "empirical evidence" that the code works and meets its performance bar; formal methods are the hardest and still unsolved end of this.
- **The codebase is the agent's memory.** Agents like to extend existing patterns, so a bad pattern will "spread kind of like a virus".
- **Correction has an order.** When an agent keeps making the same kind of mistake, consider, from strongest to weakest: making the pattern "categorically impossible" through the codebase, architecture, and data structures; static analysis (lint, compiler diagnostics, CI); rules, an automated review bot, and skills (guidance that cannot be enforced); a style guide ("really only enforceable by humans in a code review"). On seeing a bad pattern, first "write a lint rule"; it need not be cleaned up at once, but this will at least "stop the bleeding".
- **Outer-loop automation.** Connectors and scheduled routines start cloud agents that reproduce bug reports and open PRs automatically.

What the talk does not cover (observation): approval gates, who approves a merge, and writing a spec first. Nothing in the talk can therefore be used to loosen this template's approval red lines, and nothing in it directly supports this template's list of stop points.

The README of the same author's public skill set, [pstack](https://github.com/cursor/plugins/tree/main/pstack), adds a few points (observations):

- `/tdd` writes the failing test first and then the fix, which matches this template's red-then-green order.
- `/correct` fixes a recurring class of mistake at "the highest level that works," with documentation last, which matches the correction order in the talk.
- The principle `prove-it-works` requires verification against the real artifact; `encode-lessons-in-structure` requires that a lesson go into structure, not only into prose.
- Where it differs from this template: the README says "i don't believe in planning." and "the best spec is code."; the principle `never-block-on-the-human` keeps confirmation only for irreversible actions; `autopilot-full` has agents take their own PRs all the way to merged, and a separate `autopilot-stack` does the same without the merge. This template does not adopt these; see N3 and N4.

## 5. Severity

- **S1**: would break approval, safety, privacy, or truthful attribution, or would let a change merge or deploy incorrectly.
- **S2**: the rules contradict each other, or an implementer would act on the wrong text. Each S2 issue is marked as blocking a merge or the main flow, or not; blocking ones are fixed in this round and the others are logged.
- **S3**: an improvement to practice, wording, or maintainability. Logged only.

Counts for this round: 1 S1 issue (fixed); 11 S2 issues (10 fixed, of which 9 block a merge and 1 does not but is fixed in this round by the owner's decision; 1 logged); 12 S3 issues (logged); 4 practices logged and not adopted.

## 6. S1 (fixed)

**S1-1 The Cookbook told the agent to put "the local computer's host id" in Host-Id.** The rules say Host-Id carries only the id agreed for that computer, never its real host name. Section 7 of the Cookbook said "with the local computer's host id," so an implementer could well fill in the system host name; that line then enters the public commit history, and pushed history cannot be rewritten. Item 7 of the AGENTS template, the README, the adoption guide, and the task-brief template in the Cookbook had only the placeholder, without this limit.
Basis: "Attribution" and "Privacy and release" in the rules; the Cookbook is meant to be handed to an implementer on its own, so it cannot be assumed that the reader has seen the rules.
Handling: fixed. Sections 3, 4, and 7 of the Cookbook (both languages), item 7 of the AGENTS template (both languages), the README (both languages), and the adoption guide (both languages) now state "only the agreed id, never a real host name."

## 7. S2

### Blocking a merge; fixed

**S2-1 Step 8 of the loop in the README still described v2.1 severity handling.** It read "S2 (must fix): fix, rerun the same tests, and re-review; S3 and low-risk items: proceed per the review decision," the opposite of MVP iteration in the rules. Handling: rewritten to match the rules (both languages), with the one-report rule and its exceptions added.

**S2-2 The README labeled the v2.1 change summary "still applies."** The S2 handling, the list of stop points, what Host-Id carries, and how scan hits are handled in that section have all been changed by v2.2, so the label would lead a reader to follow the old text. Handling: relabeled as historical, with a statement that v2.2 takes precedence (both languages).

**S2-3 The scan clauses in the companion documents lacked "no allowlisting on the agent's own decision" and the minimum scope.** This affected sections 6 and 8 of the Cookbook, and step 7 and the "Why" table of the README. An implementer who received only the Cookbook would not see the limit. Handling: added (both languages).

**S2-4 The PR template had no place for logged items.** The rules require that items logged for the next round be listed when requesting merge approval, but the PR template had no field for them; its "Release and deployment" field also did not say that each deployment is approved separately. Basis: "Per-batch loop and severity handling" in the rules; A1: "The PR template asks how the change was tested and how to undo it." (the template should carry what the approver needs to see). Handling: the PR template (both languages) gains a "Logged for the next round" line under "Validation," and "Release and deployment" states that each deployment is approved separately. The acceptance, handoff, and spec templates were checked, agree with v2.2, and are unchanged under this item (the acceptance template separately gains one note for S2-10).

**S2-5 "Next-round log location" was missing from the companion documents.** The configuration table in the rules has this row; the list and quick start in the README, section 3 of the Cookbook, and the first-adoption steps in the adoption guide did not. Handling: added (both languages), with the default location when none is designated.

**S2-6 The companion documents stated the stop points more weakly than the rules.** Section 10 of the Cookbook said "report once" without the exception for stop-point items and scan hits; section 2 of the Cookbook did not say to list the steps immediately; section 9 of the Cookbook and steps 9–11 of the README did not say that approval must come in person, that logged items are listed when requesting merge approval, that each deployment needs its own approval, or that branches are not deleted without an instruction. Basis: A1, "An agent's approval never counts as a person's, either." Handling: added (both languages); all of it aligns the text with the rules, and no rule is new.

**S2-7 Terms were not consistent.** The README wrote "the coding cloud" (and the equivalent reversed word order in Chinese) for the cloud coding environment, and the English README called the configuration table the "adaptation table," while the rules and the other documents use "cloud coding environment" and "configuration table." Handling: unified.

**S2-8 The earlier review report did not match the public originals.** Three places: (1) it summarized A9 as "automation still keeps people at the critical approval points," but the original covers credential vaulting, a read-only token, a host allowlist, and run caps, and does not describe approval points; (2) it presented "a cloud coding environment is used as a full working environment" as the content of A6, while the original says only that a session can push its working branch and open a PR, so that sentence is an inference; (3) it listed the personal names of an article's authors, against the rule that outward-facing content omits personal names. Handling: this report is rewritten, each item is matched to the original, inferences are marked separately, and articles by an organization are cited under the organization.

**S2-9 The Cookbook did not say where the default boundary in section 1 applies and where the cloud-environment rule in section 4 applies.** Section 1 defaults to "do not push or open a PR," and section 4 says not to tell the cloud environment "not to push." Handling: section 4 now says the rule covers only the agreed branches and Draft PRs, provided that pushing and opening a PR have been authorized; without that authorization, section 1 still applies and work is prepared locally only (both languages). This is a clarification and does not widen any permission.

### Not blocking a merge; fixed in this round by the owner's decision

**S2-10 The rules did not tie an approval to a head.** The rules said "review must correspond to the current head" and "reread head/base before merging," but they did not say whether a merge approval from the user still holds if the head changes after the approval was given. Basis: A1, "An approval covers one specific commit. If new commits land that the system can't vouch for… the approval has to be given again."; the adoption checklist in A1, "dismiss approvals on new commits".
Handling: fixed. The owner decided to write it into the rules in this round. The rules gain an "Approvals are bound to a head" paragraph under "Major changes and stop points that require user approval": a merge approval is valid only for the head (commit SHA) it was given for; after a new commit, a rebase, or a base change alters the head, the approval lapses, and the change is revalidated and the user's approval in person is obtained again; a deployment approval is likewise valid only for the specific version it names. The "merging" and "deployment" items of the stop-point list, step 6 of "End-to-end workflow," and the change log at the end of the file say the same. Item 8 of the AGENTS template, the README, sections 4 and 9 of the Cookbook, the adoption guide, and the CHANGELOG follow; the PR template gains a line for the head SHA an approval covers, and "Approvals and scope" in the acceptance-record template says to note that SHA or version. The merge half is directly supported by the original in A1; binding a deployment approval to a version is an **inference**, adopted by the owner's decision. All of it is a tightening, and no red line is loosened.

### Not blocking a merge; logged

**S2-11 Hard rules exist only as text, with no adoption advice on platform mechanisms.** Basis: A3, "If something has to happen every time, make it a hook, a deny rule, or a managed setting."; the adoption checklist in A1 recommends CODEOWNERS and branch protection so that sensitive paths always need a person; poteto's correction order puts rules and skills after static checks. This repository configures no platform settings by design, and that does not change. Suggested for the next round: add an optional section to the adoption guide saying a project may back the stop points with branch protection, required checks, or the tool's deny rules. Configuring those changes policy files and repository settings, which is itself a stop point.

## 8. S3 (logged only)

1. **Convergence rules for independent review.** A cap on rounds, later rounds review only the new diff, and no repeats of findings already raised. Basis: A1, "A round cap. After three rounds, the reviewer asks the author to step back and reconsider the approach."
2. **A "pre-existing" mark for review findings.** A problem the change did not introduce is marked separately and logged without counting against this round. Basis: the tags in A1, "Important, Nit, or Pre-existing".
3. **The correction order as an optional practice in retrospectives.** In a retrospective, ask first whether this class of mistake can be made impossible to write, then whether a static check can be added, and only then turn to rules, skills, and prose. Basis: [poteto's talk](https://x.com/poteto/status/2102050467505430555); `/correct` in pstack.
4. **Examples of non-test evidence under "Specs and evidence."** Real run output, traces, and screenshots, alongside tests and not in place of them. Basis: the first layer of checks in A1, "ask it to show the output instead of saying it's done"; poteto's talk.
5. **State "you land it, you own it."** Ownership after a merge, not an extra approver. Basis: A1, "Owning the outcome. A person is accountable for every change that ships, whoever typed it."
6. **Cross-reference a progress file and checkpoints for long-running work with the handoff record.** Basis: A5, A11.
7. **Have task briefs and review prompts name what this round does not look at.** Pure style issues, for example, to reduce review noise. Basis: A3 (see the excerpt in 2.1); A1, "Noise costs more when the author is an agent."
8. **Make the cloud environment's network access a row in the configuration table.** Basis: the host allowlist in A9; A10, "Network access is limited by default and can be configured to be disabled or allow only specific domains".
9. **Provide a standalone task-brief template.** The README already notes there is none; the brief is inline in the rules and the Cookbook. Basis: what A11 requires of a task description.
10. **The default roles name specific products and models.** They can be overridden in the configuration table, but the names go out of date; the body could name roles only and keep defaults in the configuration table. Basis: this repository's own principle that roles are defined by responsibility, not by product or vendor.
11. **How to treat trailers a tool adds itself.** A6 says commits from cloud sessions carry a trailer that links back to the session transcript. This template specifies only `Code-Tool` and `Host-Id`; it does not say whether a trailer added automatically by a tool is kept, or whether a session link in public history is acceptable. This needs the owner's decision.
12. **Two points of wording in the Cookbook.** The title and opening use a nickname for the implementer, and whether to keep it is for the owner to decide; the strengthened tests use race detection, repeated runs, and switch polarity as examples, and the text could say they are examples (the rules already say "where applicable").

## 9. Logged, not adopted

The following practices come from public sources, but they would loosen this template's approval red lines or run against rules already set, so they are not adopted in this round. Adopting any of them changes a gate and needs separate approval from the user.

- **N1 Low-risk changes merge without human approval.** A1: the low tier needs no human approval once automated review and security checks pass; the article's closing also says its own repositories let owners decide which low-risk changes merge on automated checks alone. This template requires the user to approve every merge in person, and that stays. The conditions the original itself gives (lighter paths only for trusted authors, start strict and loosen with evidence, no circuit breakers yet that tighten automatically) are not met by this template.
- **N2 The author closes a false positive with a reason.** A1: "You either fix it or close the thread with a short reason, which is how you clear a false positive." This template is stricter for privacy and credential scans: any hit stops and is reported first, and is not allowlisted on the agent's own decision. That stays.
- **N3 No planning; code as the spec.** The pstack README: "i don't believe in planning." and "the best spec is code." This template keeps the spec and design review first.
- **N4 Agents carry work through to merge and wait for a person only on irreversible actions.** `autopilot-full` and `never-block-on-the-human` in pstack; A6 also says routines run without approval prompts and push to prefixed branches. This template's list of stop points is unchanged; a cloud environment may only push to the agreed branches and open a Draft PR.
