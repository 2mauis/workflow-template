## 2.2.2 — 2026-11-15
- The workflow version is still v2.2: the rules in `template/docs/workflow-v2.md`, the AGENTS template, and the other shared templates are unchanged, and the version title of the rules file stays the same.
- Splits the Cookbook into two, under this repository's `docs/` (not `template/`), each in Chinese and English:
  - For Dot: `docs/cookbook-dot.md` and `docs/cookbook-dot.en.md`. A new section 0, "Verified Dot capabilities," links every item to official OpenAI documentation (verified on 2026-11-15); the official announcement page returned 403 to automated fetching and is marked not verified, and details from third-party reports are left out.
  - For Grok Bot: `docs/cookbook-grok-bot.md` and `docs/cookbook-grok-bot.en.md`. Organized around multi-bot collaboration: a chief bot routes each deliverable to a specialist bot and accepts the work before delivering it; coding is split between a cloud coding agent that implements, a local CLI for hands-on programming, and a separate subscription for architecture and read-only review, with the same sessions reused and registered for each project; bot-to-bot overhead is kept down; each round fixes only S1 and blocking S2 issues, with S3 logged as issues; the user is told as soon as a usage limit is hit. These are stated to be a way of working, not product claims; product capabilities are limited to what official xAI pages verify, each with a link.
  - Both keep the original Cookbook's workflow, stop points, approval red lines, scan rules, and 4-case red/green exercise. Approval red lines are only tightened: automatic review or Auto Review letting an action run, custom rules, the chief's acceptance, and other bots' conclusions are not user approval; no rule may let a stop-point action proceed automatically; an expired background approval card counts as not approved; usage resets are not used, and accounts are not switched, to get around a limit.
- `template/COOKBOOK.md` and `template/COOKBOOK.en.md` are not deleted; they become short pointers to the two new Cookbooks, with no workflow content, and are not copied into projects. The text from before the split is at the pinned commit `374b69557896be784bc1d14058be1ff976a07e23`. The old paths are kept so that historical references in the review report and changelog, and links already shared, still lead to the new location.
- README (Chinese and English): the status now reads template repository 2.2.2, with links to both Cookbooks and updates to the "What is in this repository" table and the quick start. Adoption guide (Chinese and English): the opening link points to the new Cookbooks, and 0.2.0 → 2.2.2 upgrade checks are added.
- Versioning convention changed (the owner's decision): the template repository version moves from 0.2.0 to 2.2.2; its major and minor numbers match the workflow version it ships, and the patch number marks revisions of the template repository itself. "Versioning" in the README and adoption guide is rewritten to match. The version number does not mean the templates are stable; they still need to be adapted and validated in each project.

## 0.2.0 — Unreleased
- Upgrades the workflow to v2.2. The rules file is still named `template/docs/workflow-v2.md`; the version is given by the file title and the "Change log" at its end. Main changes relative to v2.1:
  - MVP iteration: each round fixes only S1 issues and S2 issues that block a merge or the main flow; remaining S2 issues, S3 issues, and small items are logged for the next round; the reviewer marks whether each S2 issue blocks a merge or the main flow; logging does not waive an item, and logged items are listed when requesting merge approval.
  - Strengthened tests and independent review form one handoff, reported once at the end of the round; stop-point items and scan hits are still reported as soon as they occur, and work that is stuck is reported early.
  - The cloud coding environment the project designates is a full working environment: it may read and write, push to the agreed branches, and open a Draft PR; it is not given "read-only" or "do not push" instructions, and that rule does not change the stop points. Confirm that the Git hosting connection is authorized for this repository before submitting; state the base branch in the task body when the task entry point has no branch picker; on an authorization denial or an unavailable branch, retry and actually verify rather than reusing an earlier failure conclusion or shelving the task.
  - Do not delete branches without a user instruction, including branches of closed PRs. Next-round items go to the location in the configuration table, or to comments on the relevant PR and the handoff record when none is set; do not change repository settings in order to log them.
  - Adds the "Terms, plans, and communication" section: interpret project-specific terms as the project defines them and confirm first when the meaning is unclear and would affect direction; do not unilaterally change a deployment or real-environment test plan that has been set; list the steps immediately when the user must sign in or authorize in person.
  - Stop points clarify that each deployment needs its own approval, and add "relaxing a test or gate guarantee"; approvals must come from the user in person, and an "approval" from another agent or bot does not count.
  - Approvals are bound to a head: a merge approval is valid only for the head (commit SHA) it was given for; after a new commit, a rebase, or a base change alters the head, revalidate and obtain the user's approval in person again; a deployment approval is likewise valid only for the specific version it names.
  - The minimum scope of the scan is listed; no hit may be added to an allowlist on the agent's own decision. Outward-facing content does not mention expense-related information or individuals' names, and omits usage figures, addresses, and cities. Host-Id carries only the agreed id, never a real host name.
  - Sources and the review basis are in `docs/reviews/v2.2-review.md` (English: `docs/reviews/v2.2-review.en.md`).

Documents use only placeholders, with a note that for local runs the host id appears in the public commit history.
