# 给 dot 的开发工作流 Cookbook

这是一份可以单独交给 dot 的开工说明。目标是把需求变成可验证、可交接的改动；不要求特定产品、部署平台或外部评审服务。文档不是权限授权，也不会自动安装工具、连接账号、配置 CI 或开启仓库保护。

中文与英文 Cookbook 描述同一流程，并引用同一套中英对照共享模板。选择一种阅读语言，不重复执行流程，也不另装一套语言专属规则。

## 1. 复制这一段开始

把本文件作为附件或全文发给 dot，再附下面这段。只需填写目标仓库和任务；还没有仓库时，保留“本地演练”。

> 请按附件 Cookbook 开工。
> 目标仓库：本地演练 / 我提供的仓库链接或本地目录
> 任务：先跑通本文阈值示例 / 我描述的具体修改
> 工作边界：默认仅本地准备、测试和交付；不要推送、开 PR、合并或部署。
> 可选授权：如果我明确填写了目标仓库及“允许推送任务分支并开 Draft PR”，才执行这两步。合并、部署、权限、凭据和外部评审服务另行确认。
> 请先确认目标和当前环境，读取项目规则，给出简短计划。能安全推进的部分直接推进，只问真正阻塞的问题。按 spec → 设计评审 → 红测试 → 最小实现 → 绿测试与回归 → 独立评审 → 证据交付执行。不能运行或没有权限的步骤明确标为未运行/阻塞，不能伪造成功。

如果你只收到本文件，没有整个模板仓，仍可用第 4 节的内联结构开始；不要为找不到可选模板而停住。

## 2. 冷启动：先读什么，缺什么怎么办

dot 应先完成：
1. 确认用户提供的仓库和任务。多个同名仓库、目标分支不明确或任务目标有实质歧义时，先问一个最小问题。没有项目就做第 5 节本地演练，不创建远程仓库。
2. 使用用户指定的电脑/环境；未指定时选已有且能访问目标的环境。先验证路径、仓库来源、当前分支和工作区状态。保留他人未提交修改，不自动清理、重置或混入本次提交。
3. 读目标仓库适用的 AGENTS.md、README、贡献/运行说明、相关 spec。已有项目规则优先；如果与本说明或用户要求冲突，说明冲突并确认，不静默替换。
4. 如果有整套模板，依次读 README、docs/ADOPTION.md、template/docs/workflow-v2.md，再按需使用 spec、验收、交接与 PR 模板。模板位置不是目标项目的固定位置。
5. 检测实际可用的测试命令和工具版本；不能仅从示例推断。列出独立评审方式、CI/required checks、合并策略和授权范围。不存在的项目项写“未配置”，不可冒充通过。
6. 给出简短目标、范围、检查计划、阻塞与预期交付。缺登录/连接时请用户通过产品支持的安全方式完成；不要索要密码、token 或私钥到聊天/文件里。

最少参数只有“哪里”和“做什么”。环境可探测；测试命令从项目读取；未指定合并策略就不合并；未指定外部评审服务就不调用；无独立评审能力可继续准备和自查，但必须把独立评审记作阻塞，不能宣称可合并。

## 3. 采用到已有项目（可选，不是开工前置）

只复制需要的模板，并与已有文件逐项合并，不覆盖项目规则：
- template/AGENTS.md.template → 项目 AGENTS.md。
- template/docs/workflow-v2.md → 项目 docs/workflow-v2.md。
- template/docs/specs/TEMPLATE.md → 项目 docs/specs/TEMPLATE.md。
- template/docs/ACCEPTANCE_TEMPLATE.md、HANDOFF_TEMPLATE.md → 项目 docs/。
- template/PULL_REQUEST_TEMPLATE.md → 平台认可的位置，例如 .github/pull_request_template.md；其他平台先确认。

记录来源完整 commit 和采用日期。可用已核验 tag 时固定 tag 和 commit，没有 tag 时固定 commit，不假定已有 release。填写测试、评审、检查和负责人。只复制文件不会使平台门禁生效。新增 App、凭据、付费能力、仓库保护和权限需要独立确认。所有采用变更也应走项目评审。

通用必需：范围、可观察验收、真实证据、独立评审、隐私检查、交付状态。
按项目可选：CI 平台、SAST/lint 工具、签名机制、部署、发布、合并策略。某项一旦被项目要求，就不是可随意跳过的检查。

## 4. 每个任务的闭环

### 角色与门禁
- 需求/设计评审：核对契约、非目标、风险和验收。
- 实现者：先测试再实现，执行项目检查。
- 独立评审者：不是实现者自查；核对当前完整改动及证据。可以是另一位人或独立内部评审会话，但后者不等于平台上另一个账号的 APPROVE。
- 负责人：决定重大变更、合并和发布。CI 通过不代替任何这些批准。

小任务也要有简短规格；权限、安全、不可逆数据操作、跨系统重构、依赖主版本、发布部署等重大变更先取得明确批准。不把 spec 的“已写”当“已批准”。

### 可直接复制的规格
```text
目标/触发条件：
非目标：
输入、输出、不变量、错误行为：
验收：需求 → 测试文件/用例 → 输入 → 预期 → 验证环境
设计评审：结论、评审来源、未决问题
风险与回退：
批准范围：
```

先写验收测试，验证红灯是预期行为断言失败，而不是缺依赖、拼错命令或导入失败。允许提交时保存红测试提交再最小修复；只允许本地准备时保存补丁/日志，别伪造 SHA。绿灯后运行项目要求的相关和完整检查，区分通过、失败、跳过、未运行、未配置。纯文档改动可说明行为红绿测试不适用，但仍验证链接、示例和隐私。

独立评审对应当前 head；没有提交则对应明确文件快照/校验和并说明限制。后续修改须重新运行受影响检查、更新评审。失败就修复再复查，不删测试、不降低断言、不跳过门禁。

### 可直接复制的交付记录
```text
目标与实际变更：
环境/工具版本：
base/head SHA（无提交则写未提交及快照标识）：
验收 → 测试 → 实际结果/日志位置：
红灯原因与绿灯结果：
完整检查、CI 和独立评审（分别列出）：
风险、未验证项、阻塞与下一步：
是否已提交/推送/开 PR/合并/发布/部署（分别回答）：
授权范围与回退方法：
```

## 5. 可运行配方：边界值从红到绿

这是隔离的软件演练，不操作设备，不验证生产，不需要第三方 Python 包。前提：已有 Python 3。缺少时先报告，不自动安装。输入契约仅为非负整数，负数和其他类型不在范围内。目标：等待时间达到阈值时返回 True。

在全新的临时目录中创建以下两个文件，不覆盖已有项目文件。先由独立评审者确认此规格和四个用例，再执行测试。缺少独立评审者时，可继续本地演练并记录实际红绿结果；独立评审仍标为阻塞，不宣称完成全部门禁。

eligibility.py（故意保留边界错误）：
```python
def is_eligible(waited_seconds, required_seconds):
    return waited_seconds > required_seconds
```

test_eligibility.py：
```python
import unittest
from eligibility import is_eligible

class BoundaryTests(unittest.TestCase):
    def test_below(self):
        self.assertFalse(is_eligible(9, 10))

    def test_equal(self):
        self.assertTrue(is_eligible(10, 10))

    def test_above(self):
        self.assertTrue(is_eligible(11, 10))

    def test_zero(self):
        self.assertTrue(is_eligible(0, 0))

if __name__ == "__main__":
    unittest.main()
```

在这个目录运行：
```sh
python3 -m unittest discover -s . -p 'test_*.py' -v
```

预期红灯：4 个测试，equal 和 zero 两项 AssertionError，退出非零。实际记录结果后，只把 eligibility.py 中的 > 改成 >=，不改测试。再次执行同一命令，预期 4 项全部通过。这只是预期，拿到 Cookbook 的 dot 必须自己运行并报告实际结果。

由独立评审者检查契约、测试不变、单运算符修复并独立复跑。此演练无需 git、网络或 CI；未做远程验证就写“CI 未运行”。如项目需要 CI，另按第 6 节适配。不要把本示例当通用输入校验库或真实硬件验收。

## 6. CI 与 PR 配方（需要用户授权）

获准推送到指定仓库并开 PR 后，使用任务分支和 Draft PR，附规格、验收映射、风险、红绿证据、限制。不要自动合并。

有现成 CI 时使用现成流程。没有 CI 时先拟定最小方案并确认是否配置；不要默默安装服务。可选 Python 演练 CI 应使用现有可信 runner、已核验版本的 Python、只读 contents 权限、超时、无 secrets、无部署；第三方 action 固定到已核验完整 SHA，禁止凭空填写 hash。不要在不可信 PR 代码上使用有权限的 pull_request_target，也不要让 fork PR 执行接触内网/凭据的自托管 runner。

检查时记录：
- 精确 head SHA、base SHA、每个检查名称、结果、运行链接和被测提交。
- push CI 可直接测原 head；pull_request CI 常测合成 merge commit，明确两者差别。
- 历史红灯不应被抹去；当前必需检查必须在当前候选提交通过。
- 旧 head 的通过、缺失检查、等待状态都不是当前成功。
- 独立分析与平台正式审批分开记录；平台要求另一账号批准时照办，不伪造或绕过。
- CI 变更、合并冲突解决或 base/head 变化后重新核验受影响结果。

## 7. 署名、签名与来源

先核对项目身份、DCO 及签署规则，不擅自更改全局 Git 身份；存在冲突时先确认。提交作者准确反映实际来源：AI 实作使用可识别的 AI 作者名称，并加 Agent: <实际来源标识>；人工使用本人选定身份及 Agent: human。人工批准不会把 AI 实作变成人工实作；不要用邮箱域名推断来源，也不要在文档或 PR 正文复制真实邮箱。

作者/trailer 是来源声明，不是密码学签名。GPG/SSH/Sigstore 等签名是否必需由项目决定；没有可用授权签名能力就报告阻塞，不生成/导出密钥、不关闭签名要求。服务端 squash/rebase/merge 可能改变元数据，合并前核对策略，合并后回读实际署名和签名验证结果。

## 8. 隐私、分享与同步

分享的是可复用方法，不是私人上下文。导出采用明确文件白名单，人工逐文件审阅并扫描秘密、真实邮箱、账号标识、内网地址、设备路径、私人日志和原始聊天。只允许示例占位符，不嵌私有项目链接。扫描只能辅助，不能保证安全。

如来源仓库混有私人内容，用全新历史的干净导出；不直接 push --mirror、复制 .git 或把整仓改公开。公开可见性、邀请他人和授予访问需另行授权。私有链接对别人未必可读；可分享经检查的本文件或干净文件包。授予许可/添加 license 属于维护者决定，本说明不代替许可证。

有多个仓库时先核对它们是同一历史的镜像还是独立导出。记录通用文件的来源 commit，按白名单做内容差异同步；保留各仓专属内容，尤其不覆盖或导出 private-context。未确认同步方向时先交付差异，不自动双向同步。

## 9. 合并、故障与停止条件

合并需明确授权及项目批准策略。合并前重新读取远端 head/base、PR 状态、当前 CI、有效独立评审、来源署名和适用保护。任何不符合就停止该动作。保留原提交的 fast-forward 只是可选策略，不能为了署名绕过 PR 或保护。

拒绝、保护失败、并发更新、权限不明、签名不符、未知命令副作用、泄密风险都应报告准确目标、原因和最小下一步。不强推、不改保护求通过、不自动切换账号绕过限制。执行结果不确定时先查状态，避免重复推送/开 PR/部署。

获准合并后回读目标分支和 PR，确认实际提交与状态，再报告。部署与发布仍单独授权。回退优先通过新的 revert 变更，经项目检查与批准；不重写历史。若只能完成一部分，交付已有补丁、规格、证据和未完成清单，不把“已准备”写成“已上线”。
